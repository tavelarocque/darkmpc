# Milestone 5c: measuring on real machines

## Why simulation was not enough

Until now every timing came from one computer pretending to be three. The three servers ran as threads or processes, and a small model delayed each message by a chosen latency and a chosen bandwidth. That is good for comparing two versions of the code, and it caught real mistakes, like the "hidden round" in the checksum optimisation. But a model only knows what you tell it. It does not know how a real kernel schedules threads, how TCP behaves over a 68 millisecond link, or what a cloud VM's network actually delivers. A benchmark that ends up on a resume has to come from machines that were really apart.

So the last measurement of Milestone 5 puts each server on its own Google Cloud VM. A script on the laptop creates the three machines, copies the committed code to them, builds it there, measures the network it got, and then runs every configuration three times. The laptop plays the traders: it deals each batch into shares and uploads one share file to each server. After each auction it downloads the three output files, reconstructs every fill, and compares them with the plain reference matcher. A run that disagrees is never recorded. That check is what makes the table trustworthy: every number in it comes from an auction that provably produced the right answer.

## The first lesson was about quotas, not cryptography

The first attempt failed before any MPC ran. Free-trial projects may use at most 8 vCPUs of Google's newest machine family per region, and the plan asked for 12. The fix was smaller machines with one physical core each. That makes these numbers a floor for the hardware: every server had less compute than a typical laptop. The script also had a real bug, exposed by the failure. When one of three VMs could not be created, the other two kept running and billing. It now deletes whatever it created if any part fails, a property worth having in any script that rents machines by the second. The second region tried for the WAN had simply run out of that machine type, a reminder that "the cloud" is a set of real buildings with real stock.

## What the numbers say

On a LAN, with all three servers in one data centre and 0.2 milliseconds between them, Stage 1 handles 1,000 orders in 0.055 seconds in semi-honest mode and 100,000 orders in 4.3 seconds. With malicious security, the version that catches a cheating server, 1,000 orders take 0.95 seconds and 10,000 take 9.9, a steady thousand orders per second. The roughly twentyfold cost of malicious security is almost all data: every multiplication is checked against a bucket of random triples, and producing those triples is most of the traffic.

The WAN tells a different story. With servers in Oregon, Iowa and Northern Virginia, every round of communication costs about 25 milliseconds, a bit under half the 68 milliseconds it takes a message to cross the country and come back. The protocol needs a few hundred rounds whatever the batch size, so even a 100-order auction takes 6 seconds. The arithmetic is trivial; the time goes into waiting for the speed of light. That is why the round count, which grows only logarithmically with the batch, was the number worth optimising throughout this project. It is also why large batches pay: the semi-honest WAN throughput grows from 17 orders per second at 100 orders to over 4,000 at 100,000, because the same few hundred rounds now carry a thousand times the work. At 100,000 orders the second limit appears, bandwidth: 2 gigabytes per server for Stage 2 take most of a minute to cross a 0.7 Gbit/s link.

## The comparison, and its limits

The one published system to compare against is the 2018 three-party dark pool by Cartlidge, Smart and Talibi Alaoui. For 1,000 orders with malicious security it reports 0.9 seconds of online time plus 4.1 seconds of preprocessing, about 5 seconds end to end. darkmpc does the same size in 0.95 seconds with no preprocessing at all, about five times faster end to end, using 566 rounds where they use 4,509. And it does more work while doing so: it hides every order's symbol among 8,192, it validates traders' inputs, and it runs minimum-fill elimination, none of which their volume match does.

A fair account also lists what favours darkmpc. Its LAN had half the latency of theirs. Its cores are newer, though there are fewer of them. And it is purpose-built, where theirs ran in a general framework. Those differences cannot be separated from these numbers, so the honest statement is about the two systems as measured, not about one algorithm beating another. On a WAN there is nothing to compare: the 2018 paper never measured one. darkmpc's 17 seconds for an actively secure 1,000-order auction across a continent is a new data point, and the reason it is that low is the round count.
